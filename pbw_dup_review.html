Rule Gap Analysis — Why xDM Misses These
The core problem: xDM's ExactCRD rule (score 100) requires both records to have a matching, non-null CRD. When one side is null, xDM falls back to name+location rules — but all of them require exact first-name match, ruling out every nickname, spelling variant, and abbreviated name. There is no fuzzy or phonetic first-name rule in the current model.
🔒
ExactCRD (score 100) — the only reliable identity anchor
Fires when CRDA = CRDB, both non-null. If either side has a null CRD, the rule is skipped entirely. All 397 duplicate pairs have at least one null-CRD side. A new rule ExactCRD_OneNull or a null-CRD flag on the record would enable targeted stewardship routing before a bad merge can occur.
397 missed
🔤
Name+Location rules (scores 85–97) — exact first-name required
ExactFirstNameLastNameMiddleNameSuffixZip (95), ExactFirstNameLastNameMiddleNameSuffixFirmState (95), ExactFirstNameLastNameMiddleNameZip (85), ExactFirstNameLastNameMiddleNameSuffixPhone (85) — all require an exact match on FIRST_NAME. "Timothy" ≠ "Tim", "Kathleen" ≠ "Kathy", "Giancarlo" ≠ "Gianni", "Nikolaus" ≠ "Niki". The phonetic encoder compounds this: Timothy → TM0, Tim → TM (different codes). ~75 nickname-variant pairs are completely unaddressable by current rules.
~75 missed
🔗
No ExactFirstNameLastNameZip rule (first+last+ZIP, no middle)
xDM has rules requiring first+last+middle+zip. There is no rule for just first+last+zip. Many same-name pairs (e.g. same-name advisor at two ML offices in the same city) are SEPARATE in xDM precisely because one record has a middle name/initial and the other doesn't, making the ExactFirstNameLastNameMiddleNameSuffixZip rule fail on middle-name mismatch. A new ExactFirstLastZip rule at score 80 would resolve a large fraction of the 160 same-firm/diff-office pairs.
~100 affected
📧
ExactEmail (score 95) — partially effective, but data gaps limit reach
ExactEmail fires when the stored email matches in xDM's master data. The 58 EMAIL-block pairs have matching emails in SFDC's CONTACT_FORMULA_VW today, yet are SEPARATE in xDM. Likely causes: email was null or different when xDM last processed the record (stale source snapshot), or one record had the email added after the last Integration run. Ensuring email is populated and current in every SFDC_NG load would let ExactEmail close ~58 of the gaps. Note: ExactEmail is currently gated per CM-2121 R5 for SFDC_NG↔SFDC_NG matching.
~58 closeable

Recommendations
Short-term — xDM rule additions
1
Add ExactFirstLastZip rule (score 80)
First name + last name + ZIP, no middle name required. Would resolve ~100 of the same-firm/same-ZIP pairs where one record lacks a middle name. Threshold of 80 routes to stewardship (not auto-confirm) — safe for review queue.
2
Unblock ExactEmail for SFDC_NG↔SFDC_NG (R5 / CM-2121)
Already proposed. Score 95 would auto-merge confirmed goldens with matching email (strictly > 90 threshold). Requires ensuring email is populated and current in every load — stale email is why ~58 email-match pairs remain SEPARATE today.
3
Null-CRD stewardship routing
Flag SFDC_NG records with null CRD on ingest — route to a stewardship queue for CRD lookup before the Integration run. Reducing null-CRD count directly reduces the size of the blind spot, independent of new match rules.
Longer-term — data quality
4
Phonetic / nickname first-name matching
A phonetic rule (Soundex / Metaphone / custom nickname table) would close the ~75 nickname-variant pairs. Risk: precision drop — "Michael" and "Michelle" share phonetic codes in some encoders. A curated nickname dictionary (Tim→Timothy, Kathy→Kathleen, etc.) has higher precision than generic phonetics.
5
Normalise ML / BofA entity hierarchy in source
45 duplicate pairs arise because "Merrill Lynch Pierce Fenner & Smith" and "Bank of America Private Bank" are separate SFDC Account records for what is operationally the same advisor population. A firm-alias lookup in Semarchy's enricher — mapping both to the same canonical parent — would let FirmState rules fire across entity boundaries.
6
Dedup SFDC before load
Several advisors have 3+ active SFDC records (e.g. Kristell Tuz, Jordan Fitzmaurice, Katherine Park, Luis Lemus). Upstream deduplication in Salesforce eliminates the problem at the source rather than relying on xDM matching to compensate.
