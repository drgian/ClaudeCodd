Methodology

How this analysis was built

Data source

The 3,029 pairs (plus 54 excluded name-collision pairs) come from the PB/Wires duplicate workbook (Snowflake, run 2026-08-05). Pairs were generated by blocking on shared CRD, shared email, shared phone, and shared xDM business team, then scored with Jaro-Winkler and classified:

BucketClassification rule
DefiniteShared email + JW(full name) ≥ 80 — OR — shared email + shared phone — OR — shared phone + JW(full name) ≥ 85 + no CRD conflict
LikelyExactLastName + JW(full name) ≥ 75 (or ≥ 90 for common last names) + at least one of: shared phone / email / ZIP / address / biz team
Name CollisionEmails differ only by middle initial or trailing digit — same name, different people at same firm. Excluded from coverage counts.

How R12 and R13 were derived

The 501 pairs that no existing or R5–R11 rule covered were classified as duplicates by the workbook using signals that had no corresponding Semarchy rule. R12 and R13 translate those workbook signals directly into match rule conditions:

RuleWorkbook signal that caught these pairsSemarchy rule equivalent
R12 (403 Likely pairs) ExactLastName + JW(full) ≥ 0.75 + shared biz team, no phone/ZIP/addr ExactLN + JW(first) ≥ 0.75 + BizTeamMembership · score 80
R13 (98 Definite pairs) JW(full name) ≥ 0.85 + shared phone, last names similar but not exact JW(first) ≥ 0.75 + JW(last) ≥ 0.75 + SharedPhone · score 85

Both rules score below the auto-merge threshold for confirmed goldens (strictly > 90), so they create suggestion groups for steward review rather than merging automatically.

Recall — pairs we may have missed

The 3,029 pairs represent only duplicates detectable via the four blocking strategies used. Duplicates that share none of these signals — different phone, no email, not on a team together — are invisible to this analysis. A name-only blocking pass (same last name + similar first name + same firm) would surface additional candidates at the cost of more false positives to review.
